# 测试设计与验证

## 何时使用

- 变更实现完成（或部分完成），需要证明"它真的能用"。
- 缺陷修复后，需要证明"修好了且没引入新问题"。
- 发布前，需要跑冒烟 / 回归。

> 本技能分两段：**先设计**（验证计划），**后执行**（验证记录）。设计可在实现前完成。

## 前置

- 必读 `.agents/rules/测试规则.md`、`安全与隐私规则.md`。
- 必读 `测试与验证/测试策略.md`、`测试分层.md`。
- 有 `实现计划.md`（含验收标准）。

## 输入

- `变更/<id>/实现计划.md`（验收标准）
- 代码 diff
- `测试与验证/测试环境与数据.md`

## 步骤

### A. 设计验证计划

1. **对齐验收标准**：每条验收条件 → 至少一条验证用例。数量不匹配就是漏测。
2. **分层设计**（按 `测试与验证/测试分层.md` 的定义）：
   - 单元测试：核心逻辑、边界值、异常分支；
   - 集成测试：模块间、DB / 外部依赖（用 mock 或容器）；
   - 端到端：关键用户路径；
   - 手工 / 探索性：UI 细节、体验、跨平台。
3. **覆盖负面场景**：错误输入、权限不足、并发、超时、断网、重复提交、大流量。
4. **定义通过标准**：什么算通过（全绿 / 覆盖率门槛 / 性能指标）。
5. **列出测试数据与环境**：需要哪些数据、哪个环境、是否需要重置。
6. **安全验证**（如涉及）：越权、注入、敏感信息泄露、依赖漏洞扫描。

### B. 执行与记录

1. 按计划执行，**逐条记录实际结果**（通过 / 失败 / 阻塞 + 证据：命令、日志、截图路径）。
2. 失败的用例：写明现象、复现步骤、初步定位（转 `缺陷定位与修复` 技能）。
3. 给出**发布建议**：可发布 / 有条件发布 / 不可发布，并说明剩余风险。

## 输出

- `变更/<id>/验证计划.md`（模板：`.agents/templates/变更/验证计划.md`）
- `变更/<id>/验证记录.md`
- 如产生可复用用例 → 更新 `测试与验证/回归测试.md`
- 如产生性能 / 安全结论 → 更新 `测试与验证/性能基准/`、`测试与验证/安全验证/`

## 检查清单

- [ ] 每条验收标准都有对应用例。
- [ ] 覆盖了负面 / 边界 / 并发场景。
- [ ] 记录了**真实执行结果**与证据，没有"应该没问题"。
- [ ] 失败项已转缺陷或明确记录为已知限制。
- [ ] 给出了明确的发布建议与剩余风险。
- [ ] 新增的可回归用例已沉淀到 `回归测试.md`。

## 边界与禁止

- **禁止**编造测试结果或"推断通过"——未执行的必须写"未执行"。
- **禁止**用"手工点了一下是好的"替代对核心逻辑的自动化验证。
- **禁止**在验证记录里隐藏失败项。
- 生产数据不得直接用于测试；用脱敏 / 合成数据（见 `测试环境与数据.md`）。
