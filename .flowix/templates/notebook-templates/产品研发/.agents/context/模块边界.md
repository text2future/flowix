# 模块边界

> **本文件回答**：系统由哪些模块组成、各自负责什么、谁依赖谁。
> 与 `模块与契约/后端/服务边界.md` 的分工：本文件描述**代码组织事实**，那份描述**对外承诺**。

## 一、模块清单

| 模块 | 路径 | 职责 | 允许依赖 |
| --- | --- | --- | --- |
| <模块> | `<path>` | <一句话> | <可依赖谁> |

> 职责描述若无法用一句话说清，通常是模块划分有问题。

## 二、依赖方向

```
<用箭头画出层级，例如：>

UI 层 → 应用层 → 领域层 → 基础设施层
                     ↑ 只允许单向
```

| 规则 | 说明 |
| --- | --- |
| 单向 | 低层**不得**反向依赖高层 |
| 禁止循环 | 出现循环 = 边界设计错误，需重构 + ADR |
| 跨层 | 必须跨层时通过**接口**，不直接引实现 |

## 三、共享与复用

| 类型 | 放哪 | 注意 |
| --- | --- | --- |
| 通用工具 | <位置> | **禁止**放业务逻辑 |
| 跨模块类型 | <位置> | 改动影响面大，需评审 |
| 模块私有 | 模块内 | 不要为了"可能复用"提前上提 |

## 四、如何判断"放错地方"

| 症状 | 说明 |
| --- | --- |
| 改 A 必须改 B | 职责重叠 |
| 出现循环依赖 | 边界画错 |
| 模块被广泛引用 | 实际是公共层，应显式化 |
| 一个模块有多个"主人" | 需要拆分 |

## 五、维护规则

- 新增 / 拆分模块 → 更新本文件，并复核 `.agents/rules/架构边界.md`。
- 边界变更 → **必须**写 ADR。
