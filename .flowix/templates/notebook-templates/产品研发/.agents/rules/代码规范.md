# 代码规范（硬约束）

> 风格问题交给格式化 / lint 工具，本文件只管**工具管不了的**结构性问题。

## 一、命名

- 命名必须表达**意图**，不是类型：`userList` 可以，`arr2`、`data1`、`temp` 不可以。
- 布尔用肯定式：`isActive`、`hasPermission`；禁止 `notDisabled`。
- 避免缩写（业界通用缩写除外：`id`、`url`、`api`、`db`）。
- 同一概念全库用同一个词（见 `.agents/context/领域模型.md` 的术语表）。**禁止同义混用**。

## 二、函数与方法

- 单一职责：一个函数做一件事；超过 ~50 行或嵌套超过 4 层 → 拆分。
- 参数超过 4 个 → 用对象 / 结构体传参。
- **禁止**用输出参数 / 全局变量传递结果（除语言惯例外）。
- 边界必须显式处理：空、0、负、超大、null / undefined、越界。
- 错误不得静默吞掉：要么处理，要么向上抛并带上下文。

## 三、注释与文档

- 注释解释**为什么**，不解释**是什么**（代码已说明是什么）。
- 每个模块 / 公开函数有简短说明（用途 / 输入 / 输出 / 失败模式）。
- 出现"魔法数"必须命名或注释来源。
- **TODO 必须带标识与原因**：`// TODO(OWNER): 原因`，并登记到 `架构决策/技术债务.md`。

## 四、结构与依赖

- 依赖方向单向，禁止循环依赖（见 `架构边界.md`）。
- 禁止跨层直接访问（如 UI 直接读 DB）。
- 公共工具放共享层；**禁止**各模块重复实现同一工具函数。
- 单个文件超过 ~400 行 → 评估拆分。

## 五、错误与日志

- 错误信息必须**可定位**：包含操作、关键标识、原因。
- **禁止**在生产代码里用 `print` 调试；用统一日志接口（见 `可观测性规则.md`）。
- **禁止**在日志中输出密钥、token、密码、完整个人敏感信息。

## 六、依赖管理

- 新增第三方依赖必须：说明理由、评估维护活跃度与许可证、评估体积 / 安全。
- 锁定版本（lock 文件必须入库）。
- 禁止为一个小功能引入重量级框架。

## 七、格式（交由工具）

缩进 / 引号 / 分号 / 行长等由格式化工具统一（配置入库，全队一致）。**不在评审中争论格式。**
