# 发布与回滚规则（硬约束）

> 第一原则：**没有回滚方案的发布，不叫发布，叫冒险。**

## 一、发布前置门槛（全部满足才可发布）

- [ ] 验证记录结论为"可发布 / 有条件发布"
- [ ] 代码评审通过（阻塞项已清零）
- [ ] 契约文档已同步（`模块与契约/` 与代码一致）
- [ ] 迁移脚本已 dry-run，rollback 脚本已就绪并验证
- [ ] 配置 / 密钥在目标环境已就位
- [ ] 监控与告警覆盖本次改动的关键信号
- [ ] 回滚方案已写清并确认可行
- [ ] 发布窗口与责任人已确定

## 二、发布顺序

标准顺序（按需裁剪，但**顺序不可颠倒**）：

```
1. 迁移（向后兼容，可回滚）
2. 后端（兼容新旧两端）
3. 前端 / 客户端
4. 打开 Feature Flag（灰度放量）
5. 观察 → 全量
```

**禁止**先发前端再发后端导致接口不一致。

## 三、灰度与 Feature Flag

- 高风险 / 大改动**必须**走灰度：白名单 → 1% → 10% → 50% → 100%。
- 每个放量步必须有**观察时长**与**放量判据**。
- Flag 必须有**Owner 与清理计划**：功能稳定后**必须**移除 Flag（否则记为技术债）。
- Flag 命名规范：`ff_<域>_<功能>`；默认值必须**安全**（默认关闭）。

## 四、回滚

- 每个发布**必须**定义：
  - **触发条件**（什么指标 / 现象触发回滚）；
  - **回滚步骤**（可执行，不含"视情况而定"）；
  - **回滚后数据处理**（尤其是已执行的迁移）；
  - **回滚验证**（如何确认回滚成功）。
- 回滚必须**可在观察窗口内完成**。
- 迁移回滚需**单独评估**：向前迁移通常不可逆，必须设计成"扩而不删"以便回滚。

## 五、不可逆发布

以下操作**必须获得用户明确确认**，并安排低峰期 + 有人值守：
- 删除字段 / 表 / 数据；
- 破坏性 Schema 变更；
- 大范围数据回填；
- 密钥轮换 / 权限收窄。

## 六、观察窗口

- 发布后**必须**观察至少一个窗口：错误率、延迟 P95/P99、资源、核心业务指标。
- 观察期内**必须**有人值守（或明确"无人值守发布"的替代方案与止损手段）。
- 观察结论必须写入发布记录。

## 七、记录

- 每次发布（含热修）**必须**写 `发布与运行/发布记录/YYYY-MM-DD-<版本>-发布记录.md`。
- 记录必须含：版本、时间、内容、顺序、灰度、结果、异常与处置、回滚（如有）。
- 热修事后必须补：根因、防回归措施、正式修复计划。

## 八、红线

- **禁止**无回滚方案的发布。
- **禁止**跳过观察窗口。
- **禁止**在生产手工改代码 / 配置而不留记录。
- **禁止**为赶时间跳过门槛——需要跳过必须用户书面同意并记录风险。
