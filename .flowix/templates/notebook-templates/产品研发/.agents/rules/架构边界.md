# 架构边界（硬约束）

> 定义"什么可以依赖什么"。违反架构边界是本项目**最容易产生长期债务**的行为。

## 一、默认分层（按需裁剪）

```
表现层（UI / CLI / 桌面壳）
      ↓ 只能向下
应用层（用例 / 编排 / 事务边界）
      ↓
领域层（业务规则 / 领域模型，不依赖框架与 IO）
      ↓
基础设施层（DB / 外部 API / 文件系统 / 队列）
```

**规则**：
- 依赖只允许**自上而下**；领域层**不得**依赖框架、DB 驱动、HTTP 客户端。
- 基础设施实现接口（依赖倒置），上层依赖**接口**而非具体实现。
- **禁止循环依赖**。

## 二、模块边界

- 每个模块有明确的**对外接口**与**私有内部**。跨模块只能走对外接口。
- 模块间通过**契约**（API / 事件 / 共享类型）通信，禁止直接访问对方内部数据结构 / 表。
- 模块不得直接读写不属于自己的数据表（见 `数据与迁移规则.md`）。

## 三、前端边界

- 页面 / 组件不得直接调用后端 SDK 之外的数据访问逻辑；数据访问统一走 API 层。
- 状态管理只存**跨组件共享**的状态；局部状态留在组件内。
- **禁止**在组件里写业务规则（业务规则在应用 / 领域层）。

## 四、后端边界

- 控制器 / handler **只做**参数校验与编排，不含业务规则。
- 事务边界在应用层显式声明，**禁止**在循环中开启独立事务造成部分成功。
- **禁止**从控制器直接拼 SQL 访问 DB；走仓储 / DAO 层。

## 五、桌面端 / 本地能力边界

- 渲染进程**不得**直接访问文件系统 / 系统 API，必须走 IPC。
- 主进程对外暴露的 IPC 通道必须**白名单化**并做权限校验（见 `模块与契约/桌面端与本地能力/文件系统权限.md`）。
- 跨平台差异必须集中处理，**禁止**散落 `if (isWindows)` 判断。

## 六、越界处理

发现需要"打破"边界时：
1. 先确认是否**真的**必要（多数情况是设计问题）；
2. 若必要 → 写 **ADR**（`.agents/templates/ADR.md`），说明代价与替代方案；
3. 经 `@org/arch` 评审通过后方可执行。

**禁止**以"赶时间"为由静默越界。
