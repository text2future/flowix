# 可观测性规则（硬约束）

> 目标：**出了问题，能在不猜的前提下几分钟内定位。**

## 一、三件套：日志 / 指标 / 追踪

| 手段 | 回答的问题 | 要求 |
| --- | --- | --- |
| 日志（Logs） | 发生了什么细节 | 结构化、可关联、有级别 |
| 指标（Metrics） | 系统状态如何 | 有基线、有告警、有看板 |
| 追踪（Traces） | 请求走了哪、慢在哪 | 关键路径全链路 |

## 二、日志

- **必须结构化**（JSON 或键值），便于检索；禁止纯字符串拼接。
- **必须包含关联 ID**（trace_id / request_id），贯穿一次请求的所有日志。
- 级别使用规范：`ERROR`（需人处理）/ `WARN`（异常但可自愈）/ `INFO`（关键业务事件）/ `DEBUG`（仅开发）。
- **禁止**在循环里刷日志；**禁止**无上限输出大对象。
- **禁止**记录敏感信息（见 `安全与隐私规则.md` 第四节）。
- 错误日志必须包含：操作、关键标识、失败原因、可定位线索。

## 三、指标

- 每个服务至少暴露：**请求量、错误率、延迟（P50/P95/P99）、资源占用（CPU / 内存）**。
- 业务关键路径必须有**业务指标**（如成功下单数、导入完成数）。
- 指标命名统一：`<域>_<对象>_<动作>_<单位>`。
- 新增失败模式必须同步新增**可观测的信号**（否则等于盲区）。

## 四、追踪

- 关键用户路径与跨服务调用必须打点。
- 新增外部依赖调用必须产生 span。
- 耗时操作必须有耗时记录。

## 五、告警

- 告警必须**可行动**：收到后知道该做什么。禁止"响而无事可做"的告警。
- 告警必须有：阈值、持续时间、严重级别、负责人、处理入口（Runbook 链接）。
- 必须设**抑制 / 聚合**，避免告警风暴。
- SLO 相关告警以**错误预算消耗**为准（见 `发布与运行/指标与SLO.md`）。

## 六、Runbook

- 每个"会告警的"系统 / 关键操作必须有 Runbook（`.agents/templates/Runbook.md`）。
- Runbook 必须包含：现象、影响判断、排查步骤、止血手段、升级路径。
- Runbook 必须**定期演练**，并随系统变化更新。

## 七、发布与可观测性

- 每次发布必须能回答："这次改动**应该**在哪个指标上体现？"
- 发布后观察窗口内**必须**看指标，而不只是"没报错"。
- 新增功能必须自带观测点，否则不算完成（纳入 `代码与规格收敛` 的检查项）。
