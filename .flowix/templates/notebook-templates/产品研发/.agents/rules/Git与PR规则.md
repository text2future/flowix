# Git 与 PR 规则（硬约束）

## 一、分支

- `main` 必须**始终可发布**；禁止直接向 `main` 推送（走 PR）。
- 分支命名：`feat/CHG-YYYY-NNN-简短描述`、`fix/BUG-NNN-简短描述`、`chore/...`、`docs/...`。
- 分支名中的变更号必须与 `变更/<id>/` 对应。
- 分支存活尽量短（小步快合），长期分支必须定期同步主干。

## 二、提交（Commit）

- 遵循约定式提交：`<type>(<scope>): <描述>`，type ∈ `feat|fix|refactor|perf|test|docs|chore|build|ci`。
- 一个提交**只做一件事**；禁止把重构与功能混在一个提交。
- 描述写"做了什么"，不写"改了哪些文件"。
- **禁止**提交：密钥、`.env`、大二进制、构建产物、个人临时文件（见 `.gitignore`）。
- 提交信息关联变更号：`feat(import): 支持本地目录导入 (CHG-YYYY-NNN)`。

## 三、PR

- PR **必须**包含：
  1. **变更说明**（做什么、为什么）；
  2. **影响面**（引用 `影响分析.md`）；
  3. **验证方式与结果**（引用 `验证记录.md`）；
  4. **回滚方案**；
  5. 关联的 `变更/<id>/` 或 `BUG-NNN`。
- PR 应尽量小；超过 ~400 行 diff 建议拆分（除非是机械性改动）。
- **禁止**在 PR 中夹带无关改动（顺手重构、格式化全文件）。
- 必须通过 CI（lint / 测试 / 构建）；**禁止**用 `--no-verify` 绕过钩子。
- 必须获得 **CODEOWNERS** 中对应 owner 的评审通过。

## 四、评审

- 评审按 `代码审查与风险检查` 技能的顺序进行（正确性 → 契约 → 安全 → 数据 → 性能 → 可观测性 → 测试 → 可维护性）。
- 阻塞项未解决**不得**合入。
- 作者必须回应每条评论（修 / 说明 / 转技术债）。

## 五、合并

- 优先 **squash** 或 **rebase**，保持主干历史清晰；**禁止**合并出无意义的 merge commit 噪音。
- 合并后删除分支。
- 合并前确认：契约文档已同步、`变更/<id>/` 已更新。

## 六、历史保护

- **禁止**对 `main` 或共享分支 `push --force`。
- **禁止**改写已推送的公共历史。
- 误提交密钥：**不是**删提交了事 —— **必须立即轮换密钥**并记入 `SECURITY.md` 流程。

## 七、版本与标签

- 版本号遵循语义化版本（`MAJOR.MINOR.PATCH`）。
- 破坏性变更 → `MAJOR`；向后兼容新增 → `MINOR`；修复 → `PATCH`。
- 发布必须打 tag，并在 `发布与运行/发布记录/` 留记录。
