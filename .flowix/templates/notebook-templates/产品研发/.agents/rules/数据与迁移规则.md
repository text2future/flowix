# 数据与迁移规则（硬约束）

> 数据是不可逆资产。**代码可以回滚，数据丢了就是丢了。**

## 一、数据模型约束

- 所有表 / 集合必须有：主键、创建时间、更新时间。
- 删除默认**软删**（`deleted_at`）；硬删必须写明理由与合规依据。
- 字段必须有明确类型、可空性、默认值；**禁止**依赖"应用层保证非空"而不加约束。
- 金额用最小单位整数 + 币种；时间用 UTC；**禁止**存本地时区字符串。
- 外键 / 唯一约束必须在数据库层落实，不能只靠应用逻辑。
- 高频查询字段必须有索引；索引变更同样走迁移流程。

## 二、迁移（Migration）铁律

1. **每次 Schema 变更必须同时提供 migrate 与 rollback**，缺一不可。
2. 迁移脚本**必须幂等**（重复执行不报错 / 不重复改）。
3. 迁移**必须可中止**：大表迁移分批执行，可暂停、可恢复。
4. 大表变更前必须评估：**锁范围、执行时长、对在线流量的影响**。
5. **禁止**在迁移里夹杂数据业务逻辑（迁移只负责结构，数据修复单独走"数据修复规范"）。
6. 上线顺序：**先迁移（向后兼容）→ 再发应用**；下线旧字段要等**所有**旧版本实例停止使用后。

## 三、破坏性变更流程

对"删字段 / 改类型 / 改语义 / 拆分表"：

1. 第一阶段：**扩展**（加新字段，双写，读旧）。
2. 第二阶段：**回填**（历史数据分批补齐，幂等、可中止）。
3. 第三阶段：**切换读取**（读新，观察）。
4. 第四阶段：**停止写旧**（双写改为写新）。
5. 第五阶段：**下线旧字段**（确认无引用后删除）。
6. 全程保留 rollback 能力；任一阶段可停。

**禁止**一步到位完成上述所有阶段。

## 四、数据修复规范

- 修复脚本必须：**先 dry-run 输出影响行数** → 备份 → 分批执行 → 可中止 → 有回滚。
- 必须**幂等**：重跑不产生副作用。
- 必须在**非高峰**执行，并有人观察。
- 修复前后必须有**数据校验**（行数、抽样、关键不变量）。
- **修复生产数据前必须获用户明确确认**（见 `开发原则.md` 不可逆清单）。

## 五、数据生命周期与合规

- 明确每个数据集的：采集目的 → 存储位置 → 保留期限 → 删除方式。
- 个人敏感数据必须：最小化采集、加密存储、访问审计、到期删除。
- 删除请求（用户注销 / 合规删除）必须**真正删除或不可逆匿名化**，并在承诺期限内完成。
- **禁止**把生产数据复制到测试 / 本地环境（用脱敏或合成数据）。

## 六、并发与一致性

- 跨表写入必须在**同一事务**内，或显式设计补偿。
- 必须评估并发场景：重复提交、并发更新丢失、竞态。
- 缓存与 DB 的一致性策略必须写明（写穿透 / 失效 / 双删）。

## 七、红线

- 未经用户确认，**禁止**执行任何生产数据删除 / 破坏性迁移。
- 未经备份与 dry-run，**禁止**执行数据修复。
- 无 rollback 脚本的迁移**禁止**合入。
