# 依赖升级计划

> 依赖升级两条路：**计划性升级**（本文件）与**紧急安全升级**（随时，见第六节）。

## 一、升级原则

| 原则 | 说明 |
| --- | --- |
| 安全优先 | 有已知漏洞 → **立即**升级，不等计划 |
| 小步快跑 | 不攒大版本跳跃（越攒越难） |
| 单独提交 | 升级不夹带功能改动（便于回滚与定位） |
| 有测试保护 | 升级前后跑冒烟 + 相关回归 |
| 有回滚方案 | 可回退（lock 文件 + 制品） |

## 二、优先级

| 优先级 | 类型 | 时机 |
| --- | --- | --- |
| **P0** | 安全漏洞（中 / 高危） | 立即 |
| P1 | 依赖的依赖有漏洞 / 停止维护 | 本月内 |
| P2 | 小版本更新（bug 修复） | 按计划（每月） |
| P3 | 大版本更新（有破坏性变更） | 单独评估 + 必要时写 ADR |
| P4 | 体验优化类 | 视需要 |

> 用 `deps:outdated` 获取真实版本后填写。风险重点关注：**原生模块 ABI、破坏性 API、构建配置、体积、许可证**。

## 四、升级流程

```
1. 触发（安全检查 / 定期计划）
2. 评估影响（breaking changes、API 变更、体积、许可证）→ 大版本写 ADR
3. 单独分支升级（不夹带其他改动）
4. 更新 lock 文件
5. 跑 typecheck + lint + test + 冒烟 + 相关回归
6. 原生模块 → 重新 rebuild
7. 灰度发布（见 .agents/rules/发布与回滚规则.md）
8. 观察（重点看性能与崩溃率）
9. 记录（本文件 + 发布记录）
```

## 五、安全检查

| 频率 | 动作 |
| --- | --- |
| CI 每次 | 自动扫描（有高危 → 失败） |
| 每周 | 人工查看 `deps:outdated` |
| 每月 | 计划性升级一批 |

## 六、紧急安全升级

```
1. 确认漏洞与影响（是否真的可用到）
2. 评估是否有可用补丁版本
3. 优先最小化升级（只升该包的最小修复版本）
4. 快速验证（冒烟 + 相关回归）
5. 走热修发布流程（可简化灰度，但**不可省回滚**）
6. 事后记录 + 防回归
```
