# Schema 迁移

> 迁移是**最容易造成不可逆损失**的改动。**必须可回退。**

## 一、迁移文件规范

```
migrations/<时间戳>_<动作>_<对象>.sql        # 或等价框架格式
```

| 要求 | 说明 |
| --- | --- |
| 只增不改 | 已发布的迁移**禁止**修改，修错要发新迁移 |
| 一迁移一目的 | **禁止**把不相关改动塞进同一个迁移 |
| 提供回滚 | 每个迁移**必须有** down / rollback |
| 可重复 | 同一迁移重复执行不应产生副作用（尽量） |

## 二、安全迁移模式

| 场景 | 安全做法 |
| --- | --- |
| 加字段 | 先加**可空**列 → 回填 → 再加约束（分步） |
| 删字段 | 先停用（代码不再读写）→ 观察 → 再删 |
| 改名 | 加新列 → 双写 → 回填 → 切读 → 删旧列 |
| 大表索引 | 用非阻塞方式创建 |
| 数据回填 | 分批 + 可中断 + 幂等 |

> **红线**：不得在一次发布里"同时改结构又改语义"，否则回滚时数据已不一致。

## 三、迁移流程

```
1. 写 up + down          5. 在真实规模数据上验证耗时
2. 本地跑 up / down 各一次   6. 记录到发布计划（含回滚步骤）
3. 评估影响（锁表 / 耗时）   7. 发布后核对行数与抽样数据
4. 备份（破坏性迁移前必须）
```

## 四、填写范例

| 迁移 | 目的 | 回滚 | 风险 |
| --- | --- | --- | --- |
| `<ts>_add_workspaces_path.sql` | 新增 `path` 列 | 删列 | 低（可空） |

## 五、维护规则

- 迁移落地 → 同步 `模块与契约/数据/数据模型.md`。
- 破坏性迁移 → 在发布计划中列为**回滚重点**，并有备份。
