# 数据修复规范

> 线上数据出问题时**怎么做才不出第二次事故**。**核心原则：先止血，再修复，全程留痕。**

## 一、红线

| 红线 | 说明 |
| --- | --- |
| **禁止**直接改生产库 | 一律走脚本，且脚本必须评审 |
| **禁止**无备份修复 | 修复前**必须**有可用备份 |
| **禁止**一次性全量执行 | 必须分批、可中断、可观察 |
| **禁止**无回滚方案 | 方案里**必须**写"怎么撤回" |
| **禁止**修复夹带结构调整 | 拆开做 |

## 二、修复流程

```
1. 止血（停写 / 关闭入口 / 回滚发布）— 优先于定位
2. 评估影响范围（多少条、哪些用户、是否仍在扩散）
3. 备份（或确认已有可用备份）
4. 写修复脚本：
     · 幂等（重复执行结果一致）
     · 分批（带 limit，可暂停）
     · 先 dry-run 输出将影响的行
     · 记录变更前后值（便于回退与审计）
5. 评审（数据类改动**必须**双人）
6. 在接近真实规模的数据上演练
7. 执行 → 分步核对 → 观察指标
8. 记录：修复报告 + 事故复盘 + 防回归措施
```

## 三、填写范例

| 项 | 内容 |
| --- | --- |
| 问题 | `<某字段被写成空值>` |
| 范围 | `<N> 条` |
| 修复 | 按日志回填，分批 500 |
| 幂等 | 是（按 id 判断当前值） |
| 回滚 | 保留变更前快照表 |

## 四、维护规则

- 每次修复后 → 写事故复盘（`.agents/templates/事件复盘.md`）。
- 修复暴露的模式问题 → 记入 `事件与问题/问题模式与防回归.md`。
- 修复脚本**必须**入库留档，便于追查。
