# 用户反馈与证据

> 需求**为什么要做**的证据来源。研发做取舍时可回查这里，判断"哪个更贴用户"。

## 一、反馈记录

| ID | 反馈 | 来源 | 日期 | 频次 | 分量 | 关联 |
| --- | --- | --- | --- | --- | --- | --- |
| FB-01 | <原话> | <访谈 / 社群 / 内测> | YYYY-MM-DD | <N 人> | 高 | ST-101 |
| FB-02 | | | | | | |

> **记录原话，不要转述成结论。**"用户希望更快"没有信息量，"导入 1000 个文件太慢"才有。
> **频次高 ≠ 优先级高**——要结合是否违背产品承诺（见 `非目标与约束.md`）。

## 二、反馈的处理方式

| 情况 | 处理 |
| --- | --- |
| 与目标一致 | 纳入 Story |
| 属于**已知限制** | 优化**文案告知**，而非改功能 |
| 违背核心承诺 | 记为永久非目标，并说明原因 |
| 偶发个别 | 先记入观察，不作为立项依据 |

> **重要**：反馈"某个能力不好用"时，先判断是 **bug / 没告知 / 真的没做**，三者处理路径完全不同。

## 三、证据强度

| 强度 | 依据 |
| --- | --- |
| 高 | 多来源一致 + 可复现行为 |
| 中 | 单一来源但多次出现 |
| 低 | 单次口述 / 推测 |

## 五、维护规则

- 反馈转化为需求 → 在"关联"列填入 Story / 变更编号。
- 反馈被拒绝 → **必须**写明理由（下次还会有人提）。
- 定期回看"占比高但一直没做"的反馈，确认是否漏判。
