# 已知限制

> **主动记录"我们做不到 / 暂时不做"的边界。** 目的是：产品如实告知用户，工程有据可依。
> **不是缺陷**（缺陷见 `缺陷队列.md`）；也**不是技术债**（债务有偿还计划，见 `架构决策/技术债务.md`）。

## 一、限制类型

| 类型 | 含义 | 能否改变 |
| --- | --- | --- |
| **永久设计** | 产品定位决定 | ❌ 不会改（除非产品方向变） |
| 范围 | 本次不做，未来可能做 | ⏳ 有后续变更 |
| 技术 | 受技术选型限制 | ⏳ 需投入评估 |
| 平台 | 外部平台约束 | ⏳ 只能缓解 |
| 性能取舍 | 为性能主动限制 | ✅ 可配置 |

## 二、限制清单

| ID | 限制 | 类型 | 影响 | 用户可见 | 缓解 |
| --- | --- | --- | --- | --- | --- |
| | | | | | |

> 填写要求：**用户可见**的限制必须同时给出**缓解方式**（配置 / 文档 / UI 提示），否则用户会认为"功能坏了"。

## 三、用户沟通要求

| 要求 | 说明 |
| --- | --- |
| 主动告知 | 首次遇到时提示，**禁止静默跳过** |
| 说明原因 | 简短说明为什么（用户能理解即可） |
| 提供出路 | 告诉用户能做什么（改配置 / 换方式） |
| 文档同步 | 用户可见的限制需同步到产品文档 |

## 四、新增流程

```
1. 确认是"设计取舍"而非 bug
2. 评估影响与用户可见性
3. 提供缓解方案
4. 登记本表 + 关联（技术债 / 未解决问题 / 变更）
5. 用户可见 → 通知产品同步文档
```

## 五、定期复审

| 频率 | 动作 |
| --- | --- |
| 每季度 | 复审"范围 / 技术"类是否可解除 |
| 产品方向变化时 | 复审"永久设计"类是否仍成立 |
| 相关变更启动时 | 检查是否可解除对应限制 |
