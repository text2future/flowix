# 无索引云存储：路径分层 + last-writer-wins 设计

历史调研见 `docs/CLOUD_SYNC_INDEX_FEASIBILITY.md`。本文描述当前选定的 path-keyed LWW 设计，并记录实现状态；上线动作以 `docs/CLOUD_STORAGE_RELEASE_PLAN.md` 为准。

一句话：**用笔记本清单、目录存在标记和目录变更戳表达结构，用对象存储的 `LastModified` 做版本序，用墓碑表达删除，并按目录变更戳减少正文列举；索引配置与文件夹外观保留在本机。**

---

## 1. 接受 LWW 之后，能删掉什么

这一步的收益比想象中大，因为它一次性去掉了协议里最贵的四块：

| 旧索引同步 | path LWW | 原因 |
|---|---|---|
| `baseRevision` 乐观锁 + `409 REVISION_CONFLICT` | **当前协议不使用** | 单个对象 PUT 原子替换对象，但没有 compare-and-swap；并发覆盖由客户端后续对账发现，不能据此保证每个并发版本都保留 |
| `operations` 表 30 天幂等回执 | **不需要** | 单对象 PUT/GET/墓碑写入可重试；多路径变化由下一轮对账收敛 |
| `changes?cursor` 单调变更流 | **不需要** | 每轮做「全量对账」，见 §4 |
| `bootstrap` 分页快照 + 起始游标 | **不需要** | 首次绑定按可中断的全量对账逐步收敛；它不是一致快照，期间变化靠后续目录扫描和周期 sweep 补齐 |
| `If-Match` / 412 重试 | **仅删除墓碑使用** | 删除使用已观察对象的 ETag 条件写入；普通内容 PUT 仍接受并发覆盖，不能保证保留每个中间版本 |

代价是**放弃云端裁决与强版本保留**：对象存储接受的最后一次 PUT 成为当前值，客户端根据本地基线、服务端 `LastModified` 和 ETag 在后续对账中尽量识别覆盖。竞态期间被覆盖的版本只有仍留在某台设备上时才有机会恢复；无条件 PUT 本身不提供冲突回执或历史版本。

2026-11-23 产品决策：接受极端并发下仅存在于云端的中间版本丢失。此决策不豁免本地未同步编辑保护、归档、完整性校验、错误报告和双设备验收；也不意味着云端提供版本备份。

普通文件对象下载时必须携带与内容一致的 SHA-256 元数据；缺失或不匹配时保留本地数据并报告错误。外部工具直接写入且不带该元数据的对象不符合此同步协议。

## 2. 键空间：层级即键

R2 没有目录，只有键。要让 list 本身就能读出结构，键必须**自带路径**（list 只返回 key/size/etag/mtime，不返回自定义元数据）。

```
u/{uid}/                                  # 用户（隔离边界，鉴权只能访问自己的前缀）
├── nb/{nbId}/                            # 笔记本
│   ├── m/manifest.json                   # 名称/图标/排序/删除标记（§3.1）
│   ├── s/{dirPath}.json                  # 文件夹：变更戳（§3.2）
│   ├── d/{dirPath}.json                  # 文件夹：存在/删除标记（§3.3）
│   └── f/{relPath}                       # 笔记正文与附件（.md / attachments/**）
```

历史版本里曾计划过 `_trash/` 和 `_state/quota.json`，两个都已否决：前者会被当成普通笔记索引（§5），后者的软计数在直连模式下没有可信来源（§7）。旧字节只存客户端版本库。

三条硬规则：

1. **键里放 NFC 归一化后的原始大小写路径**（不做小写折叠）。保留大小写后，显示名天然在键里；文件对象元数据只需 `contentHash` 和 `deleted` 两个字段。
2. **大小写冲突在客户端写入文件时处理**：macOS/Windows 文件系统本身大小写不敏感，同一目录里 `A.md` 与 `a.md` 只可能存在一个；拉取时若两个云端键映射到同一本地文件，后到者按冲突副本写入。这条从"服务端约束"降级为"客户端约定"，是无索引换来的必然结果。
3. **对象键总长不超过 1024 字节**。当前客户端把笔记本相对路径限制在 900 UTF-8 字节，为用户、笔记本和对象类型前缀留出空间；超长路径明确拒绝同步。哈希键回退与 `displayPath` 元数据映射尚未实现，也不属于首发协议。

路径段直接使用 NFC 归一化后的 notebook 相对路径（不做额外编码或哈希）；对象存储 SDK 负责请求 URL 编码。路径长度按 §2 的 900 UTF-8 字节限制。

## 3. 分层元数据对象（这不是"没有索引"，是"把必要结构摊进目录"）

必须诚实标注：这套设计仍有云端状态，分别记录笔记本身份、目录存在与目录变更戳；它去掉的是同步索引，不是所有元数据。

### 3.1 `nb/{nbId}/m/manifest.json`（每笔记本一份）

```json
{ "schema": 1, "name": "工作", "icon": "briefcase", "sortOrder": 3,
  "deleted": false, "createdAt": 1795000000 }
```

稳定 ID 由对象键 `nb/{id}/m/manifest.json` 承载，JSON body 只有 `schema/name/icon/sortOrder/deleted/createdAt`；不包含 ID、机器本地路径、索引配置或文件夹外观。`.flowix/notebook.json` 是本机身份文件，不作为 `f/` 内容上传。manifest 不含文件清单或用量摘要：文件通过 `f/` 列举，容量由对象存储实测。改名笔记本 = 覆盖这一份，LWW。

### 3.2 `nb/{nbId}/s/{dirPath}.json`（每文件夹一份，只有变更戳）

```json
{ "schema": 1, "path": "项目/2026", "lastChangeAt": 1795300123, "deviceId": "mac-7f3a" }
```

作用只有一个：**变更戳**。任何 `f/` 下的写入都要顺带覆盖一次所属目录的这份对象。轮询时只 list `s/` 前缀，戳没变的目录直接跳过（§6，这是把成本从 O(笔记) 压到 O(目录) 的唯一手段）。

三条实现时确认的约束：

- **不放条目列表。** 如果每个目录存一份"子项清单"，两个设备各自整份覆盖就会丢掉对方的条目（LWW 会吃掉结构，不只是内容）。戳只含时间戳，谁覆盖都不丢东西；条目真相永远靠 list `f/`。
- **不放索引配置或文件夹外观**。目录戳只服务于变更扫描；`.index.yaml`、独立集合定义文件、`.flowix` 配置和 `folder_index` 中的图标/封面/副标题都是本机配置，不作为云对象。
- **`lastChangeAt` 是给人看的**，门控读的是对象自身的 `LastModified`（`list` 不返回正文）。

空文件夹不会产生 `s/` 戳，但由独立的 `d/{dirPath}.json` 持久表示目录存在或删除；`s/` 仍只负责热变更戳。

### 3.3 `d/{dirPath}.json`（每目录一份，存在标记与墓碑）

目录标记用于表达空目录，也用于表示该路径已删除。客户端已实现标记读写与本地基线；它与 `s/` 分离：写文件只更新变更戳，不得意外复活已删除目录；目录删除则写墓碑，不直接删除云对象。发布墓碑前必须确认本地目录连续缺失，并确认相关远端列举完整且没有未处理的子项。网络错误、分页中断或对象存储短暂不一致都不能转成删除事实。

### 3.4 本机配置边界

`f/` 只接收笔记正文、附件和明确属于用户内容的文件。`.index.yaml`、`*.index.yaml`、`*.table.yaml`、`*.lib.yaml`、`*.workdocs.yaml` 等集合定义文件不上传；`.flowix` 下的配置、视图偏好和数据库索引不上传；`folder_index` 里的文件夹图标、封面、隐藏状态和副标题也不上传。`.flowix/database/` 里的记录正文属于用户内容，继续走 `f/`。接收远端对象时同样忽略集合定义路径，避免云端对象把配置写进本机。

目录对象只表达目录路径的存在或删除。文件夹外观在每台设备本地设置，不作为目录结构的一部分。

### 3.5 `f/{path}` 的对象元数据（每个文件自带）

```json
{ "contentHash": "sha256:…", "deleted": "0" }
```

只有两个字段，都是**判定需要**的：

- `contentHash`：完整性校验与"本地是否真的变了"的依据（ETag 对分片上传不是内容哈希，只能当变更信号）。
- `deleted`：墓碑标记。**不能用 `size == 0` 判断**——空笔记也是零字节，两者只能靠元数据区分（这也是为什么 `list` 之后要对零字节对象补一次 `HEAD`，§14.5）。

初稿列过的 `sizeBytes` / `kind` / `opTs` / `deviceId` 都没写：大小由 `list` 返回，类型由后缀决定，后两个只是审计且设备时钟不可信。元数据预算按最紧的后端算（COS 单条 2 KB / 合计 4 KB），少一个字段就少一处踩线。

## 4. 一轮同步：全量对账 + 服务器时间定序

没有变更游标，每轮通过目录戳、目录列举和本地状态做增量对账；周期 sweep 扫描完整文件前缀以修复漏掉的目录戳。判定远端变化优先使用对象存储的 `LastModified`，同秒替换使用本地记录的 ETag；设备墙上时钟只用于显示和冲突文件命名。首次绑定和 sweep 都不是一致快照，后续对账负责收敛。

```text
sync_pass():
  local = scan(notebooks)                           # stat + 本地路径状态
  stamps = list(".../s/")                          # L0：读取所有目录戳
  dirs = due_directories(local, stamps, last_scans) # 新目录、变更目录、待删确认、周期 sweep
  remote = list_each_complete_directory(dirs)       # L1：只有完整分页才证明缺失
  resolve_zero_byte_objects_with_HEAD(remote)       # 墓碑与空文件都可能是 0 字节
  plan = reconcile(local, remote, server_time)       # 纯决策，不做网络或磁盘 IO
  applied = execute(plan)                            # 传输前保护本地数据
  persist_only_successful_state(applied)              # 失败路径不推进基线
  touch_directories_for_successful_writes(applied)    # 戳失败由 force sweep 兜底
```

两个关键性质：

- **不需要云端 revision 链**。本地仍依赖每路径的同步基线和 ETag 来区分已知对象与后续替换；dirty 路径不能只按 mtime 判定。离线冲突在仍持有落败字节的设备再次观察到远端变化时，生成可见副本和版本归档。并发上传窗口里的版本保留受设备下一轮对账时机限制，见 §9。
- **单路径失败可重试，但 pass 不是事务**。成功路径可以推进状态，失败路径不推进；首次绑定、目录戳失败和分页中断由后续对账或 force sweep 收敛。戳写失败可能延迟到下一次 hourly sweep，不能笼统描述为下一轮立即修复。

### 4.1 "全量对账"不等于"全量下载"

这是最容易被误读的一点。名字叫全量对账，指的是**判定范围**是全部路径，**不是传输范围**。真正的每一次 `sync_pass` 是三层漏斗，每层只在前一层筛出候选后才付钱：

| 层 | 动作 | 付什么 | 常态规模 |
|---|---|---|---|
| L0 | `list(".../s/")` 取全部目录戳 | 1 次 Class A，**只返回键名 + mtime + size**，不返回正文 | 200 个键 ≈ 60 KB XML |
| L1 | 对 `mtime > lastSyncedAt[dir]` 的目录 `list(".../f/{dir}/")` | 0–2 次 Class A | 50 个键 ≈ 15 KB |
| L2 | 对 `remote.mtime > lastSyncedAt[path]` 的对象 `GET` | Class B，**只有这里产生正文流量** | 0–3 个对象 ≈ 0–40 KB |

稳态（没人改东西）**下行正文是 0 字节**，只有 L0 那一次元数据 list。5000 篇笔记的仓库，别人改了一篇，你这一轮实际下载的就是那 12 KB。

三条必须一起成立的约束，否则"不下全量"会退化成"下了全量"：

1. **L2 的判据只能是 mtime / hash，不能是"本地没有就下载"**。对 L1 返回但本地也有的路径，**不 GET**，只用 list 里的 size 兜底判断（size 不同 → 必然不同 → 才 GET）。
2. **本地扫描只做 stat，不算 hash**。`scan(notebooks)` 每轮 stat 5000 个文件（几毫秒到几十毫秒），比 size+mtime 没用变化就跳过；hash 只在真的要上传/下载时算一次。每轮重算 5000 个文件的 sha256 是纯浪费（约 60 MB IO）。
3. **`s/` 戳必须可靠**。戳漏更新的后果是漏检一个目录，下一轮（或周期性 sweep）补上，不会导致全量拉取。

正文全量拉只发生在三种情况，且都应该是**分批、可中断、带进度**的：

| 触发 | 拉多少 | 设计 |
|---|---|---|
| 新设备首次绑定 / 新增笔记本 | 该笔记本全部正文（5000 篇 ≈ 60 MB） | 按目录分页，每页 50 篇；每篇落盘后立刻写 `lastSyncedAt`；中断后重启从断点继续，不重来 |
| 凭证换桶 | 未定义 | 客户端重置本地基线并开启禁删宽限期；跨桶复制不属于首发同步协议，见 §13.4 |
| 本地状态库丢失 / 损坏 | 全部 | 同上首次绑定，但可以先按"本地已有同路径同 size"跳过，实际只补缺失的 |

**轮询成本还能再降**：30 秒固定轮询，一天活跃 8 小时 = 960 轮，L0 的元数据流量约 57 MB/天（1.7 GB/月，COS 上下行计费约 ¥0.85/月，R2 egress 免费）。加一层自适应退避即可砍到 1/3：连续 N 轮无变化就把间隔 30s → 60s → 120s 封顶，本地一有 dirty 或收到变更立刻回到 30s。最坏"别人改了我 2 分钟才看到"，换来流量与请求数三倍下降。

如果后面还想更省，唯一的正路是**订阅桶事件通知**（R2 Event Notifications → Queue，COS → Ckafka/SCF）当唤醒信号，把 30 秒轮询降成事件驱动 + 低频兜底 sweep。但事件是至少一次、可能乱序、可能丢的，**只能当加速，不能当正确性来源**：漏掉的事件必须由周期性 `list("s/")` 兜回来。第一期不要做。

### 4.2 对账是谁在算：计算在客户端，输入不全在本地

一句话：**`sync_pass` 是一个纯客户端的函数，但不是一个纯本地的函数。** 本地提供"我有什么"，远端提供"你有什么"，**裁决逻辑完全在客户端**，云端没有任何判定代码。

| 参与方 | 提供什么 | 有没有业务逻辑 |
|---|---|---|
| 客户端本地 | 路径 → size/mtime/hash 的 dirty 表、`lastSyncedAt`、冲突副本命名与落盘 | **全部裁决都在这里** |
| 存储层（R2/COS） | 键列表 + `LastModified`（唯一可信时钟）+ 对象元数据 | 没有，只回答"有没有、多大、何时写的" |
| Worker | 校验 token/设备/权益、签发前缀受限凭证、续签时告知配额余额 | 只做准入，不做对账 |

三层里只有第一层有"逻辑"，后两层是哑的。这正是能换桶的根因：索引版把裁决放进了 DO 的 SQL 事务（比对 `baseRevision`、分配 `last_seq`、靠 UNIQUE 约束判冲突），换云等于重写一个一致性层；本设计把裁决移回客户端，换云只是换一个"读事实"的适配器。

四条推论，都要在实现里兑现：

1. **判据的权威时钟在服务端，不在本地。** 设备墙上时钟只用来给冲突副本起名、给人看时间，排序一律用 `LastModified` / 响应 `Date` 头。把设备时钟当判据是这类设计最常见的崩法。
2. **同一份状态在两台设备上可以得出不同结论**（COS 的 list 最终一致会放大这一点）。这不会造成"分歧固化"：下一轮重判，最终都对齐到同一个 `LastModified`；代价是可能出现一两轮多余的上传/下载。
3. **没有服务端兜底，客户端的 bug 会直接写坏云端。** 所以 Worker 仍要保留最小防护栏：前缀归属、size 上限、可选 hash 校验、配额。这些是防呆，不是对账，别混为一谈。
4. **把 `reconcile(localView, remoteListing) → actions[]` 写成纯函数**，输入输出都是普通结构，网络请求与落盘留在外层。这样"三层漏斗"和删除分支可以用表驱动测试覆盖，不需要起 mock 存储。

反过来说，**唯一能纯本地完成的形态是"云备份"（单向上传）**：每轮只扫本地 dirty 表往上推，根本不需要问远端有什么，判定 100% 在本地。它换掉的不只是索引，还换掉了双向同步本身——这也是它只能作为独立模式、不能替换现有多端同步的原因。

### 4.3 决策表（已落地为 `reconcile` 纯函数）

`flowix-sync/src/reconcile.rs::reconcile(local, remote, server_now) → plan` 把上面的伪代码落成一张表。输入只有两样东西：`LocalView`（本地 `stat` 结果 + 基线 + 待删集合 + 是否允许删除）、`RemoteListing`（这次真的列过的目录、列到的对象、以及 HEAD 得到的单键证据）；输出是动作序列、需要写戳的目录、新基线、新待删集合。函数不做 IO、不读时钟——`server_now` 是响应 `Date` 头。

| 本地 | 远端 | 动作 | 理由 |
|---|---|---|---|
| 无 · 无基线 | 有 | `download:new` | 首次见到 |
| 无 · 有基线 | 有 | `write-tombstone` | 本地删了这个文件，要把删除传出去（见下） |
| 无 | 墓碑 | 丢行（`forget`） | 两边都没了，行是废纸 |
| 无 | 缺失（目录已列） | 丢行（`forget`） | 同上 |
| 干净 | 有 · 内容一致 | 只推进基线 | 同 size、戳未推进、ETag 未变 |
| 干净 | 有 · 内容不同 | `download:remote-new` | 本地没有未发布的改动，接受远端 |
| 干净 | 缺失 · HEAD 404 | `delete-local` | 远端确认缺失后立即删除 |
| 干净 | 缺失 · 目录未列 | 无动作 | 没看过的目录不构成证据 |
| 干净 | 墓碑 · 晚于基线 | `delete-local` | 显式删除，一次即可 |
| 干净 | 墓碑 · 早于基线 | `upload:resurrect` | 墓碑是陈旧的一方 |
| 脏 | 缺失 | `upload:resurrect` | 未上传的编辑永不用删除解决 |
| 脏 | 墓碑 | `upload:resurrect` | 同上，脏数据优先于墓碑 |
| 脏 | 有 · 内容一致 | 推进基线并清 dirty | 同 size、戳未推进、ETag 未变 |
| 脏 | 有 · 远端时间更晚 | `download:conflict` + 冲突副本 | LWW 里远端赢 |
| 脏 | 有 · 同一秒 · ETag 变了 | `download:conflict` + 冲突副本 | 同秒被别人替换（见下第 4 条） |
| 脏 | 有 · 同一秒 · ETag 未变 | `upload:local-ahead` | 远端没动，本地才是新的一版 |
| 脏 | 未知（目录未列） | `probe` | 盲写可能覆盖更新的远端；一次 HEAD 更便宜 |
| 任意 | 首次绑定 / 换桶宽限期 | 不删 | 见 §13.2① |

三处与伪代码不同，都是实现时才确认必须这么定：

1. **"干净"是"能不能删"的前置条件，不是"传不传"的前置条件。** 干净 + 内容不同一律接受远端，哪怕远端 `mtime` 不比基线晚。否则一台设备会反复把旧内容当"修复"推上去，两台设备对推不收敛。
2. **脏 + 缺失／墓碑 = 复活，不看时间。** 伪代码只说按墓碑时间判，但脏意味着有未上传的编辑，删掉就是数据丢失。"删了之后另一台又改"会复活文件，这个代价可以接受。
3. **`probe` 是新增动作，而它的答案只是单键证据。** 目录没列过时，脏文件先 HEAD 一次再决定。HEAD 404 进 `RemoteListing.missing_keys`，**不能**顺手把整个目录标成"已列"——那会让同目录其它文件被误判为删除。反过来，HEAD 失败（500/超时）进 `unknown_keys`：目录已列但这一键状态未知，不能被目录判据读成"缺失"，否则一个 500 会删掉本地文件。对目录列表已列、但单项缺失的情况，也会 HEAD 确认后才立即删除。
4. **同秒冲突靠 ETag 判，不靠 contentHash（2026-11-22 修正）。** `LastModified` 只有秒精度，两台设备在同一秒写同一个键会产生**同一个戳、不同的字节**；而 `list` 不返回元数据，`contentHash` 在这一刻是 `None`，伪代码里"按 hash 字典序 tiebreak"根本无法执行。改成：每次传输后把远端 ETag 记进 `v4_path_state.remote_etag`，下一轮若**戳相同而 ETag 变了**，判定对象已被替换 → 远端赢且**必须留冲突副本**。ETag 在这里不作为内容哈希使用（分片上传的 ETag 不是 md5），只回答"这个键还是不是我留下的那个对象"。没有 ETag 基线的老数据退回"本地赢"，避免把常见的"远端没动、本地刚改"误判成冲突。
5. **只读凭证下不发任何写动作（2026-11-22 补充）。** 超额后服务端不再签写权限（§7），但计划层如果照常产出 `upload`，每一轮都会 403、重试、再 403，用户侧只看到"同步一直转圈"。所以 `plan_pass` 先看 `credentials.can_write()`：为假时把所有 `Upload` / `WriteTombstone` 转成 `defer:read-only`，并且**不写目录戳**——否则每轮都会让其他设备白重列一次目录。下载不受影响，"只读"指的是不能发布，不是不能收。

#### 4.3.1 本地删除也要走墓碑（2026-11-22 补充）

上面的伪代码只写了"只有远端 → GET"，实现时确认这条不够：**本地删了文件、云端还在**时，如果不写墓碑，下一轮会把它当成"远端新增"下载回来（笔记复活），改名则表现为旧路径重新出现、变成两份。这不只影响改名——离线删除是最常见的场景，而"删除时立刻写墓碑"这条路径在离线时必然失败，没有本地发件箱就没有补投机会。

所以判据是**本地缺失 + 有基线**（"我同步过它，然后它从磁盘上消失了"），动作是当前轮次写墓碑：

- 立即 `write-tombstone` → 其他设备拿到正向证据，一次观测就删；
- 墓碑是 `f/` 下的写入，所以要 touch 该目录的戳（"删本地文件不需要写戳"只对**收到**墓碑的一方成立）；
- 宽限期（首次绑定/换桶）内不动，否则空桶会把本地整本判成"云端已删"的反面；
- 写墓碑前再次检查本地路径；如果文件在扫描后恢复，则本轮不发布删除。
- 目录状态未知或确认请求失败时不记录成功扫描，下一轮会重查。

如果云端 ETag 与本机基线不同，或旧版本本地状态缺少 ETag，优先下载云端内容并提示用户该文件已在其他设备更新；用户仍可再次删除。只有云端与已知基线一致才发布墓碑，直连及只读代理均使用观察到的 ETag 条件写入；条件失败保留状态并在后续同步重试。ETag 缺失时不发布直连墓碑。内容上传仍是无条件 PUT，本规则不提供云端版本历史。

改名和删除在当前同步轮次发布，不再等待五分钟；离线删除仍通过墓碑传递。

#### L1 门控的三条硬约束

`directories_to_scan(local, remote_stamps, scanned, force)` 决定这一轮列哪些目录，候选集是**远端戳 ∪ 本地目录**，不是只看戳。三条约束都是踩出来的：

1. **只看戳会死锁。** 本地新建的目录在云端没有 `s/` 对象，只看戳就永远不会列它，它下面的文件永远读作"远端未知"，首篇笔记永远传不上去。列表里带上本地目录，代价是每个新目录一次 list，换来的是"空目录"这个事实。
2. **判据锚在"上次扫描时刻"，不是"上次看到的戳"。** `戳 > 上次看到的戳` 会漏掉落在同一秒的写入；`戳 >= 上次看到的戳` 会让每个目录每轮都重列，L1 的白名单和 O(目录数) 成本一起失效。正解是 `戳 + 2s ≥ 上次扫描时刻`，未变目录直接跳过，同秒竞争多触发一次重列就安静了。
3. **失败的目录读取不能推进扫描基线。** 如果列表失败，或缺失对象的 HEAD 失败，本轮不记录该目录已成功扫描，让后续同步重试。墓碑是正向证据；删除端写墓碑会推进目录戳，接收端应用墓碑不需要再次写戳。

#### 4.3.2 收敛性验证

规则级测试证明每条分支对，证明不了两条分支不互相打架。`flowix-sync/src/reconcile_simulation.rs` 用两台设备 + 一个存储跑真实的多轮 pass（含 `probe` 后重判、目录戳、`LastModified` 单调、可选 list 滞后），断言：

| 场景 | 断言 |
|---|---|
| 新笔记同步到第二台 | 两台设备与桶三方一致，静默后 3 轮 0 动作 |
| 本地新目录、云端无戳 | 能上传，且不会被判成删除 |
| 两台离线各改同一篇 | 收敛到后写者，输的一方留下冲突副本，之后 0 动作 |
| A 删除、B 有未上传编辑 | B 复活文件，A 再拉回来，且不算冲突 |
| 墓碑 | 对方第一次观测就删，无需等窗口 |
| COS 列表暂时漏项 | HEAD 找到对象后继续下载，不误删本地副本 |
| COS list 滞后 10s | HEAD 找到对象并下载最新内容 |
| 宽限期（空桶 + 有基线的设备） | 20 个文件一个都不删，也不开窗口 |
| 离线删除 | 同一轮写墓碑，对方一次观测就删，静默后 0 动作 |
| 改名（删旧 + 建新） | 旧路径被墓碑、新路径上传，对方最终只有一份、无冲突副本 |

删除不再等待确认窗口；针对列表漏项和本地文件恢复的测试覆盖了两处竞态。

## 5. 删除、移动、文件夹改名

### 删除 = 写墓碑对象，不删键

```
PUT f/{path}   body 为空
   customMetadata: { deleted: "1", deletedAt: 1795300123, deviceId: "mac-7f3a" }
```

原因：键删掉之后，"云端删了"和"我本地有但还没传"无法区分，下一轮对账会把文件重新上传（这是无索引方案第一个崩的地方）。墓碑对象零字节、几乎没有存储成本，list 也照常返回。

判定：墓碑的 `LastModified` 比本地 `lastSyncedAt[path]` 晚 → 本地删（删除前写一个版本，见下文"保留旧字节"）；否则 → 本地新增覆盖墓碑（复活）。

同一路径反复建删会一直覆盖同一个键，不会产生对象堆积。墓碑不做清理（一轮全量对账之后，没人再需要区分"更早的删除"）。

### 移动与改名

首发按路径变化收敛：新路径上传，旧路径按删除流程写墓碑。当前不做服务端 CopyObject、`_move/` 意图日志或原子目录改名；文件夹改名涉及的对象可能分多轮收敛，短时间内两端目录结构可能不一致。目录标记接入时也必须覆盖改名行为。若产品要求原子改名或崩溃后续作的移动事务，再单独设计并实现；它不是首发正确性前提。

### 保留旧字节：走版本库，**不要**建 `_trash/`

云端侧不保留任何历史 —— 这是 LWW 下明确的取舍，**恢复只能靠客户端本地归档**。但本地归档的正确落点是已有的版本库，不是新建一个 trash 目录。三条理由，前两条是硬的：

1. **`_trash/` 点不中隐藏名单。** `HIDDEN_FILE_PATTERNS` 只有 `.*`、`*~`、`*.tmp`、`*.swp` 这类模式，`_trash` 一个都不匹配。移到那里的文件会被索引成普通笔记、被 watcher 判成"外部新增"、下一轮被当成新的本地文件上传到 `f/_trash/...` —— **删除变成了复制**，并且会同步到其他设备，越删越多。
2. **改成 `.trash/` 能隐藏，但也失去了唯一价值。** 隐藏目录不进索引，用户看不见、没有恢复入口，那它相对版本库没有任何优势，只多一份要维护的清理逻辑。
3. **版本库不用改就能做这件事。** `flowix-core/src/memo_file/versions.rs` 已经能存任意字节：删除前写一个 `MemoVersionSource::RemoteDeletion` 版本，用户从「文件历史」恢复，**路径不变、笔记 id 不变、双向链接不断**。trash 目录恢复回来是"另一个文件"，id 变了，反链全断——这恰恰是用户最不能接受的。

版本库的保留策略分两种：`ConflictBackup` 不裁剪，保证远端覆盖前的本地编辑可恢复；`RemoteDeletion` 与普通版本共用 `MEMO_VERSION_LIMIT = 20`，避免远端删除留底无限增长。旧 `CloudConflict` 来源仅为读取既有归档保留。

如果产品一定要"最近删除"这个 UI，做**索引层的一张视图表**而不是目录：`recently_deleted(path, deleted_at, version_id)`。字节仍然只有版本库一份，30 天后从视图消失、字节还在版本库里。这样"要不要显示"和"数据还在不在"是两件独立的事。

### 一次删太多：暂缓，但不要整轮失败

一轮里要删掉已知文件的 20 个以上、且超过一半，多半是两种情况之一：用户真的删掉了一个文件夹，或者这一轮的扫描/清单悄悄少了半个笔记本。**在一轮之内这两者长得完全一样**，所以两种硬答案都错：

- 整轮返回错误（旧实现）—— 用户删一个 100 文件的文件夹就能让这个笔记本**永久**同步失败：没有 checkpoint，下一轮算出同一批删除，同样的错，除非把文件放回去；
- 直接执行 —— 一次坏扫描就能把笔记本清空。

现在的做法是只把删除动作转成 `defer:mass-deletion`，其余上传/下载照常执行并 checkpoint，每个被拒的路径写 `pending_since` 让下一轮重新打开所在目录。整轮结论从 `Err` 变成"同步正常，N 项删除待确认"（`PassReport.plan.stats.mass_deletion_deferred`，桌面侧同时置 `deletion_deferred`）。

放行只有一个入口：`PassRequest.allow_mass_deletion`，由调用方在**问过用户**之后置真；引擎自己永远不会猜。前端把「确认删除」接到这个字段之前，大批量删除会一直停在待确认状态——数据不丢，也不会静默变成"删了但没生效"。

## 6. 枚举成本：O(目录数) 而不是 O(笔记数)

这是整套设计能不能成立的算术。客户端 `coordinator.rs` 的轮询是 30 秒一次，按每天活跃 8 小时、5000 篇笔记、平均每目录 25 篇（约 200 个目录）计算：

| 拉取方式 | 每轮 list 次数 | 每月 Class A | R2 月成本 | COS 月成本 |
|---|---|---|---|---|
| 直接 list `f/` 全量（5000 篇） | 5（1000/页） | 43.2 万 | **$1.94** | **¥0.43** |
| 先 list `s/`，只展开变过的目录（约 2 个） | 1 + 2 | 8.6 万 | **$0.39** | **¥0.09** |
| 同上但只有 1 个目录变（常态） | 1 | 2.88 万 | **$0.13** | **¥0.03** |

COS 的读写请求都是 0.01 元/万次（≈ 1 元/百万次），R2 Class A 是 $4.50/百万次（≈ 32 元/百万次），相差约 30 倍。**"list 重"这件事在 R2 上是成本问题，在 COS 上不是**——同一份设计在两个后端的可接受边界不同，这也是为什么成本判断必须跟着后端走，不能写死。

关键性质：**成本随目录数增长，不随笔记数增长**。2 万篇、800 个目录仍然是一页 list。只有当单个笔记本目录数破 1000 时才需要分页（那时按笔记本分片即可）。

写路径：一次保存 = 1 次 `PUT f/` + 1 次 `PUT s/`（200 次/天 → 6000 次/月 → $0.027）。总成本约 **$0.15–0.25/用户/月**，仍是会员价（$29/年 ≈ $2.4/月）的十分之一量级。

热键：同一目录的戳是唯一可能的竞争点。规则是**每个 push 批、每个目录只写一次戳**（批量导入 100 篇同一目录 = 100 次 PUT + 1 次戳写），避免撞上 R2 的"同一键并发写 1 次/秒"。戳写失败不影响正确性（下一轮漏检一个目录，再下一轮全量 list 兜底）。

## 7. 配额与计费

没有索引就不能在写事务里算全量用量，只能按对象存储实测配额。写路径上没有 Worker（§8 直连），所以**服务端不存在"逐对象写前返回 402"这个位置**：服务端在签发凭证时检查用量。客户端也会用凭证附带的配额，在计划阶段决定"这一轮不发布"。

### 7.1 当前实现

| 件 | 状态 |
|---|---|
| 签发时返回 `usedBytes` | **已实现**：使用最近 5 分钟的对象存储快照；快照不存在或过期时，签发前对用户前缀重新实测，不以账本值授权 |
| 超额或实测不可用时降级为只读 | **已实现**：`usedBytes >= limitBytes`、计量状态未知/失败或来源不是对象存储时均改签 `read` 凭证，响应保留用量与计量状态。`limitBytes <= 0` 视为"未配置容量"，但没有有效的实测仍不能写 |
| 定时刷新用量 | **已实现（R2）**：每 5 分钟分页扫描账户，按 `users/{uid}/` + `u/{uid}/` 两个前缀实测累加；签发凭证时另有 5 分钟新鲜度门槛与过期即测 |
| 大对象数计量 | 每批最多 10 页，保存游标及累计值供下次请求或定时任务续跑；达到 80,000 对象记录告警。计量未完成时客户端在后续同步中约 30 秒后重试申请凭证。只有完整扫描结果可授权写入，新鲜度从扫描开始计算，超过 5 分钟则重扫并保持只读。部署前需应用 Cloud 的 `0023_storage_measure_progress.sql`。 |
| 只读时的上传与删除 | 官方云只读时普通 Upload 仍转 `defer:read-only`；已确认的本地文件删除通过服务端条件写墓碑，并更新目录戳。失败保留待处理状态，目录戳有本地持久重试。自定义 S3 只读时仍延迟所有发布；COS 代写尚未启用。 |
| 降级对用户可见 | **已实现**：`PassReport.writable` → `CloudSyncStatus.writable` → 状态栏「仅本地」提示 |
| `_state/quota.json` 软计数 | **已否决**：直连模式下没有可信写入点，自报数字比没有数字更危险 |

### 7.2 为什么必须实测，而不是继续读账本

v4 客户端直连 `PUT`，`reservation → complete` 状态机被删掉（§8 最后一段），因此**没有任何请求会更新 D1 的 `storage_bytes` 账本**。cron 若继续读账本，v4 用户的 `usedBytes` 永远停在迁移时的值，`limitBytes` 永不触发，配额形同虚设。

实现取的是**实测值直接取代账本值**，不是"两者取大"。取大会形成棘轮：账户一旦达到过峰值，之后删文件也降不下来，会永久锁死在只读。实测覆盖两个键空间，成功时就是完整答案；失败（后端不可枚举、对象数超过 5 页上限）时不返回部分和，也不拿账本值签发写凭证——低估会让超额账户看起来合规。账本估算只供设置页解释。

**上线门禁**：大陆 COS 桶的 ListObjectsV2 签名覆盖 query 参数，而 `cosRequest` 只签 `host`，直接带 query 会 403。COS 分支暂时返回 `null`；签发端因此只给读凭证。启用大陆写入前必须补 query 签名并完成真实桶计量与读写冒烟。

**刷新周期与成本**：cron 每 5 分钟处理一页 40 个账号，所以全量刷新一轮约为 `用户数 / 40 × 5 分钟`（1000 账号约 2 小时）。单账号一次实测最多 10 次 `list`（两个前缀 × 5 页），一页 40 账号约 440 个 subrequest，在单次调用 1000 的预算内。直传凭证的快照超过 5 分钟时会额外即时实测；因此新用户不必等到 cron 首轮完成即可开始同步。超过分页上限的账户保持只读，直到计量范围可完整覆盖。

## 8. 鉴权：控制面签发，数据面直连

结论：**能直连，而且应当直连。** Worker 在同步热路径上只承担一件事——签发一个"只能访问自己前缀、只能执行同步所需动作、15 分钟后自动失效"的凭证。之后所有 list/get/head/put 由客户端直接打到对象存储，不经过 Worker；删除通过写墓碑完成。

现状代码已经走了一半：`flowix-cloud/src/infra/blob-storage.ts` 的 `issueUploadCapability` / `issueDownloadCapability` 在 `BLOB_DIRECT_TRANSFERS=true` 时返回预签名 URL 而不是代理路径。剩下的一半是"每对象、每请求签一次"——那是热路径上的额外往返，加上 L0 每轮都要 list，往返还要乘二。

三种凭证形态，只有第二种能真正做到极简：

| 形态 | 谁签名 | 每次操作要问 Worker 吗 | 能否 LIST | 吊销窗口 |
|---|---|---|---|---|
| 预签名 URL（现状） | Worker（持父凭据） | **要**，每个 URL 一次 | 能，但每个前缀一个 URL | 立即（未使用即失效） |
| 前缀受限临时凭证（推荐） | 客户端（持临时 AK/SK + token） | **不要**，只有续签时一次 | 能，任意前缀 | = TTL |
| 长期 AK/SK 下发 | 客户端 | 不要 | 能 | 无（不可撤销） |

第三行是唯一绝对不能做的：父凭据一旦到了客户端，前缀隔离就只剩"客户端自觉"。

**R2 和 COS 都能做第二行，但签发成本差一个数量级：**

- **R2**：`POST /accounts/{id}/r2/temp-access-credentials` 支持 `prefixes` / `objects` / `ttlSeconds`（最长 7 天）/ `permission`。更关键的是**本地签名**路径——用父 token 的 secret 对一个 JWT 做 HS256，`secretAccessKey = sha256(jwt)`、`sessionToken = base64("jwt/" + jwt)`、`accessKeyId` 沿用父 AK。于是 Worker 用 WebCrypto 就地签出一份临时凭证，**不打上游 API、无延迟、无配额**；只有本地签名支持按 `actions` 精确到 `GetObject/HeadObject/ListObjectsV2`。
- **COS**：走 CAM 的 `GetFederationToken` / `AssumeRole`，policy 把 `resource` 限到 `qcs::cos:<region>:uid/<appid>:<bucket>/u/{uid}/*`。代价是**每次签发要打一次 `sts.tencentcloudapi.com`**（几十毫秒、有 QPS 上限），所以 COS 侧要么接受这点延迟，要么把 TTL 拉长到 30 分钟摊薄。

签发请求返回凭证、写入模式和配额快照；路径协议不返回 epoch 或迁移标记：

```json
POST /v2/storage/credentials
→ { "endpoint": "...", "bucket": "...", "region": "...",
    "accessKeyId": "...", "secretAccessKey": "...", "sessionToken": "...",
    "expiresAt": 1795300923000, "prefix": "u/<uid>/",
    "mode": "read-write",
    "quota": { "usedBytes": 812345678, "limitBytes": 5368709120 } }
```

对象操作优先读取客户端缓存，只有凭证进入 5 分钟续签窗口时才请求签发。连续活跃 8 小时、TTL 15 分钟时，约每 10 分钟签发一次，即约 48 次/天；相比每 30 秒轮询 `sync/status` 的 960 次/天仍显著减少。间歇使用时，实际次数取决于首次使用时间和凭证到期时间。

必须钉死的规则：

1. **prefix 只能由服务端从已验证的用户 ID 派生**，绝不能取客户端传的路径片段。用户 ID 必须是单一路径段，前缀保留末尾 `/`，确保 `u/ab/` 不会覆盖 `u/abc/`。
2. **TTL 15 分钟，提前 5 分钟续签**。TTL 就是吊销窗口。
3. **权限最小化**：客户端只拿 `Get/Head/Put/List`；同步删除是写墓碑，不授权 `Copy/Delete`、批量删除、分片上传或桶级配置。账户注销另走服务端清理权限。
4. **写成功的证据只信存储层**：`LastModified` 与 `contentHash` 元数据，不信客户端上报的时间。
5. **每个 S3 请求在发送前解析凭证并使用新的 SigV4 时间戳**。一次长 pass 可在分页、文件和后续 HEAD 之间续签；pass 仍固定开始时的桶、前缀、读写模式与配额快照。续签必须保持同一读写模式，不能在 pass 中途静默降级。
6. **意外提前失效时只重试一次**。仅当对象存储返回 `400/403` 且结构化错误码为 `ExpiredToken`、`InvalidToken` 或 `TokenRefreshRequired` 时，客户端绕过被拒绝的缓存凭证申请新凭证，并用新时间戳重签同一请求一次。`AccessDenied`、配额错误和其他失败不触发刷新重试；自定义 S3 静态凭证不会因此重试。

直连要付出的代价，必须写在产品文档里：

| 失去的 | 后果 | 兜底 |
|---|---|---|
| 写前配额拦截 | 客户端可在 TTL 内超配额写入 | 软计数 + cron 纠偏；超限后**续签时不再签写权限** |
| 即时吊销 | 注销/踢设备/降级后，旧凭证在 TTL 内仍可读写 | TTL 尽量短；注销流程 = 删数据 → 等一个 TTL → 再清一遍 |
| 服务端校验 hash/size | 客户端写了错的 `contentHash`，换桶迁移时可能跳过该对象 | 只影响该用户自己的数据；迁移前后抽样比对 |
| 服务端审计 | "谁在何时写了什么"Worker 不再知道 | 开存储侧日志（R2 Logpush / COS 日志投递） |
| 完成回调 | — | **反而可以删**：现状 `issueUploadCapability` 还要客户端回调 `/complete`，让 `verifyReadyBlob` 再 head 一次；新设计里 `LastModified` 就是事实，没有"预留→确认"状态机 |

最后一条值得单独说：直连不是"把代理换成一个 URL"，而是**顺带删掉了 reservation → complete 那条状态机**。这和无索引是同一个方向的简化——云端每少一个状态，就少一处需要迁移、对账、重置的东西。

运行环境上没有障碍：同步引擎跑在 Rust（`flowix-sync` + `reqwest`），直连对象存储不受 CORS 与混合内容限制，`x-amz-*` 头可以随意带。只有将来出 Web 版才需要配 bucket 的 CORS（`PUT/GET/HEAD` + `x-amz-*` + `x-amz-meta-*`），并单独评估"session token 存浏览器内存"的 XSS 面。

## 9. 这套设计会丢什么（必须让产品知道）

| 风险 | 后果 | 兜底 |
|---|---|---|
| 两设备离线改同一文件，且双方都有旧基线 | 后上传者成为当前值；另一端观察到新 ETag/时间后留冲突副本 | 必须在再次同步前保留本地文件；真实双设备验收确认 |
| 两台设备在同一路径并发 PUT，或都首次创建该路径 | 无条件 PUT 没有比较基线；中间版本可能被覆盖。上传后 HEAD 只证明读取时对象 hash 与本机相同 | 客户端验证 PUT 后 HEAD 的 `contentHash`，不匹配则不推进基线；这能发现 PUT 与 HEAD 之间的覆盖。HEAD 之后发生的替换由下次对账处理。存储本身仍不保留被覆盖版本 |
| 远端覆盖发生在本机成功 HEAD 之后 | 下次对账看到远端替换时，旧本地字节先进入有上限的版本历史，再应用新对象 | 本地替换已留底。它保护仍存活的设备，不构成云端备份；全部设备离线/损坏前尚未留底的中间版本无法从桶中恢复 |
| 用户保存与远端下载同时发生 | 远端决策可能基于旧本地状态 | 落盘前按当前字节重新比较，并在 notebook 文件锁内条件替换；检测到变化就保留本地文件、下轮重新对账 |
| 无服务端 revision 裁决 | 客户端只能在后续对账时发现替换，不能即时提示；对象存储只保留当前值 | 当前路径适合多端收敛，不等同于有历史的云备份 |
| 目录戳写失败 | 本轮不会展开该目录；未变戳可能使后续增量轮询继续跳过它 | 每小时 force sweep 兜底；同步状态需暴露戳写错误 |
| 客户端 bug 批量写墓碑 | 云端整本"看起来被删"，且**云端没有历史可回滚** | 每台设备的本地版本库是唯一恢复源（`ConflictBackup` 来源不裁剪）；因此"覆盖/删除前必须 archive"是硬要求 |
| 软配额可绕过 | 凭证签发后到期前可继续写入；多设备并发和大对象可超过限额 | 5 分钟内实测只减少陈旧判断，不是强硬上限。产品需接受有界超额；要求硬上限时应由数据面预留额度或校验每次写入 |
| 文件夹改名收敛期间 | 多个路径对象分轮更新 | 允许短暂不一致；对象模型接入后验收重连与重复重试 |

## 10. 迁移路径

这是首发直接采用 path-keyed LWW 的清洁上线，不提供旧协议兼容或导入：当前没有真实旧用户，旧协议会增加双写和覆盖风险。

1. 新同步使用 `u/{uid}/` 对象前缀；首发账户从本地扫描建立云端副本。
2. 不清理、不覆盖、不迁移现有云端对象；`users/{uid}/blobs/` 旧命名空间保持原样，后续若要回收需单独审批清理范围。
3. 首发客户端只运行一套同步引擎。当前 path 协议没有 epoch 协商字段；版本门禁检查唯一引擎、凭证前缀与对象 schema。
4. manifest、空目录和索引配置排除已经进入 path 实现；真实双设备、故障恢复和 10,000 文件验收仍是发布门禁，见 `docs/CLOUD_SYNC_ACCEPTANCE.md`。COS 未纳入首发并保持写入关闭。

|---|---|---|

| 轮询成本 | $0.03–0.05/月 | $0.13–0.25/月 |
| 变更检测 | `changes?cursor` 增量 | 目录戳 + 按需 list |
| 原子批量 | 一次 push 一个事务 | 无，靠对账自愈 |

| 最坏数据丢失 | 编辑冲突（有副本） | 内容覆盖前留副本；笔记本/目录元数据存在后写覆盖 |
| 换桶 / 换云 | 需自建单写者（Redis 锁、行锁）与序号生成 | 客户端检测凭证变化并进入禁删宽限期；跨桶数据复制另行运维 |

**判断**：如果产品能接受"两台设备同时改同一篇时后写者覆盖"，这套设计的复杂度显著低于旧索引同步（云端几乎不需要状态机，客户端协议层可以砍掉一半）。客户端可在后续同步发现覆盖并留冲突副本，但没有服务端 revision 裁决。

## 13. 多后端可移植性（R2 ↔ COS ↔ 其他 S3 兼容）

这一节回答"能不能灵活换桶、换到腾讯 COS"。结论：**能，而且这正是本设计相对索引版的核心优势；但有三处必须按后端能力修正，其中 list 一致性是最关键的一处。**

### 13.1 为什么索引版搬不动，而这套能搬

不是"数据库"这三个字的问题，是**能力依赖**的问题：

| 需要的能力 | 索引版（epoch 3） | 本设计 |
|---|---|---|
| 单写者串行化（跨设备互斥） | **必须**（Durable Object 天生一个实例） | 不需要 |
| 多语句事务 / SAVEPOINT | **必须**（一次 push 一个事务 + 逐条 207） | 不需要 |
| 条件写 CAS（`If-Match`） | 不需要（自己在事务里比 revision） | 不需要（PUT 即 LWW） |
| 单调变更序号 / 二级索引 | **必须**（`changes?cursor`、`last_seq`） | 不需要（目录戳 + list） |
| 计数器与配额强一致 | **必须**（`usage_bytes` 在事务里加减） | 软计数 + 每日纠偏 |
| 对象存储基本能力 | 只存 blob | PUT / GET / HEAD / LIST |

DO 在腾讯云上没有等价物：要复刻"每个用户一个单写者 + SQLite 事务 + alarm"，只能自己用 Redis 分布式锁 / MySQL 行锁 + 定时任务拼一个，成本和故障模式完全不同（锁超时、脑裂、迁移时的状态清理）。**索引版真正锁死的不是"数据库"，而是"单写者"这个能力**；本设计没有任何一处需要它。

### 13.2 三处必须按后端修正

**① COS 的 ListObjects 是最终一致性（决定性差异）**

R2 文档明确 list 强一致；COS 的 `GET Bucket` 文档明确写着：上传后立刻 list，结果里**可能不包含刚上传的对象**。当前实现会在目录列表报告文件缺失时，对该对象执行一次 `HEAD` 确认：`HEAD` 返回对象就按最新内容继续对账，返回 404 才立即删除本地副本；`HEAD` 失败会保留文件，并让目录下次重查。首次绑定或切换存储目标后的保护期仍保留。

```text
目录列表缺失 + HEAD 返回对象  → 按对象内容继续对账
目录列表缺失 + HEAD 返回 404  → 立即删除本地副本
目录列表缺失 + HEAD 失败      → 保留本地副本，下一轮重试
墓碑存在                       → 按墓碑时间判删
```

这取消了删除确认等待，同时避免把一次延迟列表直接当成删除。

**② COS 的自定义元数据上限：单条 2 KB、合计 4 KB**

文件对象元数据目前只有 `contentHash` 和 `deleted`。若要为 manifest 或目录对象增加自定义元数据，先按 COS 4 KB 总上限核算，不要按 R2 的 8 KB 预算。

**③ `LastModified` 是秒级精度，且各后端时钟不同**

- 变更戳的判据是"戳 ≥ 上次扫描时刻 − 2 秒"，不是"戳 > 上次看到的戳"。用 `>` 会漏掉落在同一秒的写入；而把 `>=` 用在上次看到的戳上，会让**每个目录每轮都要重列**，L1 直接失效。锚在扫描时刻上两者都避开，见 §4.3。
- 冲突判定不要用严格大于：`remote.mtime >= lastSyncedAt[path]` 且 hash 不同 → 接受远端；相等时用 `contentHash` 字典序做稳定 tiebreak（保证两台设备得出同一结论）。
- **跨桶复制会改变对象的 `LastModified`**。客户端检测到凭证指纹变化时会重置本地基线并开启禁删宽限期；它不负责复制或校验对象，见 §13.4。

### 13.3 后端适配层要暴露什么

同步协议只需四个对象操作和能力声明：

```ts
interface ObjectStore {
  list(prefix: string, cursor?: string): Promise<{ objects: ObjectMeta[]; next?: string }>;
  head(key: string): Promise<ObjectMeta | null>;
  get(key: string): Promise<ReadableStream>;
  put(key: string, body: Bytes, meta: Record<string, string>): Promise<void>;
  capabilities: {
    listConsistency: "strong" | "eventual";   // R2=strong, COS=eventual
    metaBytesPerField: number;                // R2=8192, COS=2048
    metaBytesTotal: number;                   // R2=8192, COS=4096
    mtimePrecisionMs: number;                 // 两者都是 1000
    maxListKeys: number;                      // 都是 1000
    presign: "s3-query" | "sts" | null;       // COS 用临时密钥，R2 用 S3 预签名
    credentialMinting: "local-sign" | "upstream-call" | "presign-only";
    // R2 = local-sign（Worker 内 HS256 签 JWT，零上游调用）
    // COS = upstream-call（打 sts.tencentcloudapi.com，几十毫秒）
    // B2/MinIO 等 = 视是否支持 STS，最差退化为 presign-only（每请求一次 Worker）
  };
}
```

硬删除供账户注销等服务端管理操作使用，不属于客户端同步接口。对账、墓碑确认和元数据预算按 `capabilities` 分支，而不是按后端名字分支。

### 13.4 凭证换桶与区域迁移

客户端在凭证指纹（后端、桶、前缀）改变时调用 `v4_rebind_credential`：清除旧桶的删除重试记录、重置本地时间基线并开启禁删宽限期。这个保护不负责复制对象，也不代表区域迁移已经完成；上线验收只验证重绑到隔离空桶时不会删本地内容或覆盖未上传编辑。跨桶复制、校验、回滚和源桶保留时间属于独立运维流程，目前未实现，也不属于首发范围。因此设计中不再预设未落地的 `_state/epoch.json` 协议。

### 13.5 还搬不动的地方（保持诚实）

| 项 | 影响 | 处理 |
|---|---|---|
| 跨对象原子性 | 无（本设计本来就不依赖） | 对账自愈 |
| 预签名 / 临时凭证 | R2 可在 Worker 内本地签名（零上游调用），COS 需打 STS（几十毫秒），其余厂商可能只能预签名 | 适配器按 `credentialMinting` 分三档；退到 presign-only 时热路径每请求多一次 Worker 往返，功能不受影响、成本与延迟变差 |
| 分片上传阈值与 ETag 语义 | COS 分片 ETag 非 MD5 | 只用自定义 `contentHash`，不信 ETag |
| list 最终一致 | 列表漏项可能导致误删 | §13.2 对缺失对象执行 HEAD 确认 |
| 对象版本控制 | COS 可选开启，R2 无等价物 | 不依赖，恢复靠客户端版本库（§5） |
| 账号/订单/权益面 | 仍在 D1（不参与同步正确性） | 换云时单独迁，与本设计解耦；这里本来就必须有个数据库，重点是它不进同步链路 |

## 14. 执行层的状态决策（已定，2026-11-22）

`reconcile` 是纯函数，执行层要落盘三样东西：基线状态、冲突副本、删除留底。这三条不是实现细节，定错了后面很难改，所以单独记下来。

### 14.1 基线状态：新建 v4 三张表，**不复用** `v2_note_states`

| 维度 | `v2_note_states`（epoch 3） | v4 需要 |
|---|---|---|
| 主键 | `note_id` | `path`（v4 里**没有 note_id 概念**，路径就是身份） |
| 版本 | `revision TEXT NOT NULL` | 不存在，只有 `LastModified` |
| 顺序 | `last_seq INTEGER NOT NULL CHECK(>=0)` | 不存在，没有服务端序列 |
| 删除 | `deleted=1`（永久墓碑行） | `pending_since`（删除处理失败时用于重试扫描） |

四条否决理由：

1. **键模型不同。** v4 引擎拿到的是路径，`note_id` 在它内部根本不存在。硬复用要在每次读写时反查 `note_id`，等于给热路径加一次索引查找，还引入"路径存在但 note_id 查不到"的新错误态。
2. **NOT NULL 列要伪造。** `revision` 和 `last_seq` 在 v4 里没有对应物。塞 hash 当 revision、塞 0 当 last_seq，代码能跑，但这两列的语义就废了——将来任何人读它都会拿到错的答案。**假数据比没有数据更危险。**
3. **状态不能混读。** v2 的墓碑语义和 v4 的删除重试状态不同：v2 把行标 `deleted=1`，v4 会误判为"远端删了"；v4 清掉行，v2 会误判为"从没见过这个 note"。因此内部并跑期间也使用分离的状态表，首发只运行 v4。
4. **部署风险。** 首发直接使用 v4 状态表。内部切换前保留 v2 表供当前开发路径使用；切换后可让旧表留空，是否删除另作代码清理，不要求为旧版客户端回滚协议。

三张表，按更新频率拆（写放大只在最热的那张上）：

```sql
-- 每路径一行，随文件改动而变（热：每次保存）
CREATE TABLE v4_path_state (
  notebook_id       TEXT    NOT NULL,
  path              TEXT    NOT NULL,  -- NFC 归一化后的键，大小写保留
  display_path      TEXT    NOT NULL,  -- 磁盘上的真实相对路径（见下）
  content_hash      TEXT,              -- sha256:<hex>，可空：只有算过才有
  local_size        INTEGER NOT NULL,  -- 记录 local_mtime 那一刻的本地大小
  local_mtime_millis INTEGER NOT NULL, -- 记录那一刻的本地 mtime
  last_synced_at    INTEGER NOT NULL,  -- 远端 LastModified（服务端时钟）
  pending_since     INTEGER,           -- 删除或恢复处理需要重试的起始时刻，可空
  remote_etag       TEXT,              -- 上次传输后远端对象的 ETag（§4.3 第 4 条）
  PRIMARY KEY (notebook_id, path)
);
CREATE INDEX v4_path_state_pending
  ON v4_path_state(notebook_id) WHERE pending_since IS NOT NULL;

-- 每目录一行，随目录内任何改动而变（温：每批 push）
CREATE TABLE v4_dir_scan (
  notebook_id       TEXT    NOT NULL,
  dir               TEXT    NOT NULL,
  stamp_millis      INTEGER NOT NULL, -- 上次看到的 s/{dir} 的 LastModified
  scanned_at_millis INTEGER NOT NULL, -- 上次真的列过它的时刻（门控锚点）
  PRIMARY KEY (notebook_id, dir)
);

-- 每笔记本一行（冷：绑定、换桶、宽限期）
CREATE TABLE v4_notebook_state (
  notebook_id            TEXT PRIMARY KEY,
  grace_until             INTEGER,  -- 首次绑定 / 换桶后的禁删期
  credential_fingerprint  TEXT      -- sha256(backendId|bucket|prefix)
);
```

三个非显然的决定：

- **`credential_fingerprint` 是必需的，不是优化。** §4.3 说"换桶时必须清空 `pending_deletions`，否则旧桶的待重试记录会触发新桶目录重列"。但"谁来清"必须有落点。存一行指纹、每次取凭证时比对，变了就清 pending 并重置 `grace_until`——这比要求每个调用方记得清可靠得多。
- **`local_size` + `local_mtime_millis` 是 dirty 判定的唯一依据，原表漏了。** 初稿只存"远端 LastModified"，可它回答不了"本地这个文件自上次同步后动过没有"——而 `LocalFile.dirty` 正是要这个。判据是 `size != local_size || mtime != local_mtime_millis`，用 `!=` 而不是 `>`：从备份恢复的文件 mtime 会往回走，那是编辑不是"没变"。代价是多传一次，收益是不丢编辑。
- **`display_path` 不是冗余，也不能省。** 键做了 NFC 归一化，而 macOS 磁盘上的文件名是 NFD——两者字节不同，打开文件只能用磁盘上那一份。它同时是超长路径（键是哈希，§2 规则 3）唯一的名字来源。
- **`pending_since` 用可空列 + 部分索引，不建独立表。** 删除重试标记和路径状态是同一时刻的同一个事实；分表就要两段写，中间崩了会出现"文件已不在、但待重试记录还在"或反过来。

### 14.2 冲突副本命名：时间给人看，序号保唯一，**字节进版本库**

旧索引同步用 `{stem} (Flowix conflict {operation_key}).{ext}`，`operation_key` 由 `operation_id` 派生（`conflict_files.rs:22`）。path 同步不生成 `operation_id`，所以冲突名不再绑定内部请求标识。

建议形态：

```text
Q4 规划 (冲突 2026-11-22 19-56-20 mac-7f3a).md
Q4 规划 (冲突 2026-11-22 19-56-20 mac-7f3a 2).md
```

- 时间里的 `:` 换成 `-`（Windows 不允许），格式 `%Y-%m-%d %H-%M-%S`——**给人看的，不承担唯一性**。
- 唯一性由**落盘前查重**保证：`while path.exists() { n += 1 }`。不能指望时间戳：一次重连可能同时处理许多冲突文件，同设备同秒完全可能。加随机串能唯一，但用户要在文件树里认它。
- **可见冲突副本是用户数据，必须参与同步上传**。v4 在 notebook 路径旁创建唯一命名的 Markdown/附件副本，正常扫描会将它上传；版本库的 `ConflictBackup` 另作本机恢复兜底。漏传副本会让冲突内容只留在一台设备。
- 真正保住字节的是**版本库**：覆盖前写 `ConflictBackup`（不裁剪）；收到远端删除前写 `RemoteDeletion`（与普通版本共享 20 条上限）。文件名只是入口，用户删掉副本也不丢数据。

### 14.3 删除留底

见 §5「保留旧字节」：不建 `_trash/`，删除前写版本。要"最近删除"UI 就再加一张视图表。

**实现状态：** `v4_adapter.rs::archive` 将未发布冲突映射到不裁剪的 `ConflictBackup`，普通远端替换映射到受 20 条上限约束的自动版本，远端删除映射到同样受限的 `RemoteDeletion`。普通更新不生成可见冲突文件，避免每次远端编辑都在文件树复制一份旧笔记。

### 14.4 执行层落地（2026-11-22）

`flowix-sync` 侧、桌面端 `LocalStore` 与 `SyncManager` 接线均已完成；桌面协调器现在只调 path 引擎。发布资格仍取决于 §14.7 的真实环境验收。

| 件 | 位置 | 说明 |
|---|---|---|
| 键规则与状态类型 | `flowix-sync/src/v4.rs` | `normalize_key_path`（NFC、保留大小写、拒绝 `..`、900 字节路径上限）、`V4PathState`、`V4NotebookState`、`build_local_view`、`credential_fingerprint` |
| 三张表 | `flowix-sync/src/store/v4.rs` | 快照读取、批量 upsert、原子替换 pending 集合、目录戳 upsert、`v4_rebind_credential`（换桶三件事一次完成）、按笔记本清空 |
| 对象原语 | `flowix-sync/src/object_store_ops.rs` | `upload` / `download` / `head` / `write_tombstone`，`parse_http_date` |
| 执行器 | `flowix-sync/src/v4_apply.rs` | `apply(http, context, local, plan, snapshot, now)` + `LocalStore` trait + `conflict_copy_path` |

三个实现时才定下来的点，都是会静默坏数据的：

1. **`LocalStore::read` 必须连 stamp 一起返回，且二者来自同一个打开句柄。** 先 `read` 再单独 `stat` 会在中间留一个窗口：用户此刻保存，我们就把**新的** mtime 记在**旧的**字节旁边，文件被标成 clean，那次编辑永远不传。用 `fstat` 同一个 fd 就不存在这个窗口；读取期间文件被 rename 替换也没关系——句柄还是旧 inode，内容与 stamp 一致，下一轮 stat 到新 inode 自然判脏。
2. **`upload` 必须以 `HEAD` 收尾，不能拿 `PUT` 响应的 `Date` 当基线。** `PutObject` 不返回 `Last-Modified`，而 `Date` 是秒级，可能比 `list` 报的值早一整秒。于是下一轮看到 `remote.mtime > baseline`，判成 `download:remote-new`，把刚上传的字节拉回来——每次保存都发生。多一次 `HEAD`（Class B，约 $0.000002）换准确的基线，这类 bug 整个消失。
3. **`apply` 永不返回 `Err`。** 一个 40 MB 附件超时不能卡住同批另外 200 个文件；失败进 `ApplyOutcome::failures`，成功的照常落库，失败的下轮自然重进 plan——因为每个动作都是幂等的。

另有两个细节：墓碑的判定读 `deleted` 元数据而不是 `size == 0`（空笔记也是零字节）；元数据前缀由服务端下发（`metaPrefix`，R2 是 `x-amz-meta-`、COS 是 `x-cos-meta-`），客户端不按后端名分支。

### 14.5 一轮 pass 的编排（2026-11-22）

`flowix-sync/src/v4_pass.rs` 分三层，每层能单独测：

| 层 | 函数 | 干什么 |
|---|---|---|
| 决策 | `plan_pass(source, credentials, store, request)` | `list s/` → 绑定/换桶 → 门控 → `list f/{dir}/` → 墓碑消歧 → `reconcile` → `probe` 后同轮重判 |
| 落库（纯） | `state_updates(scanned, prepared, applied)` | 算要写的基线行、要删的行、目录扫描记录、要写戳的目录 |
| 执行 | `execute_pass(env, request, prepared, now)` | `apply` → 按上一行落库 → 写戳 |
| 入口 | `run_pass(env, request, now)` | 上面三步串起来 |

桶侧只通过 `ObjectSource` trait 访问（`list`/`head`/`put`），生产实现 `DirectSource` 就是 SigV4 直连；测试用内存假桶，所以"列目录失败""HEAD 500""零字节对象""分页"这些分支都能在进程内断言。

六个实现时才定下来的点：

1. **目录列举必须带 `delimiter=/`。** S3 是扁平键空间，`list("f/notes/")` 默认连 `f/notes/deep/*` 一起返回；不带分隔符时列根目录等于列整本笔记本，L1 门控就白设计了。`s/` 的列举则要递归（不带分隔符），一次拿全部目录戳。
2. **零字节对象要逐个 `HEAD` 消歧。** `list` 不返回元数据，墓碑和空笔记都是 0 字节。不消歧的后果不是"多一次请求"，而是**把墓碑当空笔记下载下来，把本地笔记覆盖成空**。代价是每次重列目录时为每个 0 字节对象多一次 Class B（空笔记很少）。
3. **`probe` 的答案必须在本轮重判。** 否则"目录没列过时的脏文件"要白等一个轮询间隔。HEAD 404 → 进 `missing_keys`；HEAD 失败 → 进 `unknown_keys`（见 §4.3 第 3 条），并把这一轮剩下的 probe 丢掉、下轮再说——不在同一轮里重试，避免抖动。
4. **落库时基线只写给"没有动作"的路径。** 转移过的路径由 `apply` 写自己的精确状态（远端戳 + 真实 hash）；**失败的**转移绝不能留基线，否则下一轮会把旧 stat 当成"已同步"，把没做完的活悄悄丢掉。
5. **服务端时钟优先，缺失就禁删。** 排序只用 `s/` 列举响应的 `Date` 头；某个网关把 `Date` 吞了就用设备时钟继续同步（上传下载都安全），但**关掉删除**——不可信的钟不能授权删除。
6. **写戳的代价是一个目录一次，且自己写过的目录下一轮会重列一次。** 戳写失败只记 warn：漏检的目录下一轮或每小时的全量 sweep 兜底，不会丢数据。`force` 的 sweep 就是一次递归 `list f/`，把每个目录都算作"已枚举"。

另外两个安全阀：

- **凭证指纹改变 → 禁删宽限期。** 客户端本地的 `v4_rebind_credential` 用来保护换桶后的首轮同步；它不负责复制对象，空桶回绑后的数据重建仍需通过验收。
- **`unknown_keys` 优先于目录判据。** 目录列过、但某个键的 HEAD 失败时，不能因为"目录列了它不在"就判缺失。

### 14.6 生产接线（2026-11-22）

`run_pass` 的调用方分两层，因为「谁登录了」在 `flowix-sync` 里，「磁盘长什么样」在桌面端：

| 层 | 位置 | 负责 |
|---|---|---|
| 引擎侧 | `flowix-sync/src/manager/v4_engine.rs::SyncManager::v4_pass` | 取凭证、单飞、构造 `DirectSource`、调 `run_pass` |
| 桌面侧 | `flowix-desktop/src/commands/cloud/path_sync_runner.rs::run_passes` | 选笔记本、`stat` 扫描、`MemoLocalStore`、sweep 节奏、状态上报 |

四个实现时才定下来的点：

1. **pass 必须单飞，而且是进程级的一把锁。** `execute_pass` 结尾用 `v4_set_pending_deletions` **整表替换**待删集合；两轮并发会互相抹掉对方的待重试记录，使 HEAD 失败或代理墓碑写入失败的路径不能及时重试。代价是不同笔记本也串行——pass 是带宽瓶颈，单用户感知不到。
2. **在每个对象请求边界续签，不要求凭证覆盖整轮 pass。** 列表分页、HEAD、GET、PUT 和 PUT 后的 HEAD 都重新解析凭证；缓存距离到期 5 分钟时才向控制面申请新凭证，签名时间取各请求发出时的当前时间。一个 pass 固定初始桶、前缀、访问模式和 quota 快照；若写权限凭证在中途无法按原模式续签，该次操作失败并保留待同步状态，不切换到只读凭证继续执行。缓存仍绑定 `session_generation`，登出或切换账户即作废。初始签发先请求 `read-write`，被拒时可回退 `read`，网络错误不重试。
3. **扫描只做 `stat`，并复用共享的同步路径白名单。** 该白名单让发送端与接收端对索引配置保持同一边界；`attachments/` 不出现在文件树里，但附件正文仍同步，`attachments-cache/` 继续排除。远端文件动作在发请求前校验路径，目录标记应用也执行相同判定。
4. **下载后要主动通知文件树。** 云端写入走的是自写抑制路径，watcher 不会报事件；不补 `file-management-changed` 的话，笔记在磁盘上、在索引里，就是不在界面上。

节奏与安全：

- **每小时一次 force sweep**（递归 `list f/`，§9 的兜底），其余轮次靠目录戳。
- **轮询节流 60 秒**：协调器 30 秒轮一次是为了看游标，对象列举按 30 秒重复纯属白花钱；本地编辑本来就会单独触发一轮（`scoped`）。
- **同步失败进入状态**：path 的扫描、列举、文件应用、目录标记与 manifest 错误汇总到 `lastError`，状态栏 tooltip 展示原因；部分成功仍保留成功计数并继续处理其他路径。

path 引擎已是唯一同步引擎，不提供用户可切换开关。剩余工作是完成真实验收并冻结候选版本；索引配置与文件夹外观保持本机；旧版兼容、数据导入、双写和用户灰度都不进入首发范围。
